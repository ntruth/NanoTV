## 0. 执行摘要

### 0.1 模块现状

当前模块已经具备一条完整链路：

- **接入**：13 个源（网页源为主），统一 `CatalogProvider` 协议；多镜像、健康度检测、单源 TLS 放行。
- **浏览**：首页 / 分类 / 标签 / 榜单 / 搜索 / 更新日历；跨源搜索、跨源总榜、今天新增。
- **元数据**：详情页字段、正文阅读、人物与机构匹配、离线艺人库、跨源人物档案。
- **状态**：播放进度、稍后看、手动标记已看、足迹、手动片单、关键字聚合片单、关注分类 / 人物 / 片商。
- **播放**：内置查看器播放，支持外挂字幕、音轨、HDR、缓存、悬停预览、失败兜底；单部视频可下载进图库。
- **工程**：列表快照、离线降级条、封面缓存 LRU、预取下一页、源健康面板。

### 0.2 五个判断

1. **护城河是「多源 + 本地」，不是内容库。** 单个站点随时可能失联或改版，JavDB / Stash 的内容规模短期追不上，但「一个入口看多个源、状态全在本地」是它们不做的。
2. **最大体验断点是同片重复。** 同一部作品出现在多个源时，跨源搜索与榜单会并排出现多张卡，用户要自己判断「哪个才是同一部」。
3. **详情页是终点，不是入口。** 没有「同女优 / 同片商 / 同题材」的继续浏览，用户每次都回到列表重新找。
4. **轻记忆缺失。** 只有进度和稍后看，没有本地评分、短评、片段标记；这几项在 Stash、JavDB 与社区脚本里都是高留存功能。
5. **自动化是空白。** 新内容只能靠进入源或看日历发现；没有「关注的人这周更新了什么」的一屏简报，也没有下载队列。

### 0.3 如果只补六件事

| 优先级 | 补什么 | 为什么 | 直接参照 | 状态 |
| --- | --- | --- | --- | --- |
| P0 | 跨源同片归并 + 选源播放 | 把 13 个源真正变成一个库，消除重复卡 | JavDB 番号库、MetaTube 番号匹配 | 待做 |
| P0 | 详情页相关轨道 | 让浏览能继续，提升单次会话深度 | Stash 人物 / 片商 / 标签页 | 待做 |
| P1 | 下载队列 | 现在单部串行，下载时其它按钮全禁用 | Whisparr 下载队列 | 待做 |
| P1 | 适配器回归自检 | 网页源改版后会静默变空列表 | JavSP 每日抓取器测试 | 待做 |
| P1 | 智能片单 2.0 | 现在只支持关键字，无法按女优 / 片商 / 标签落单 | Plex Smart Collections、Stash filter | 待做 |
| P2 | 本地评分 / 短评 + 片段标记 | 从「看过」升级为「记得住」 | Stash rating / markers | 待做 |

### 0.4 战略建议

- **不要做「另一个 JavDB」**：番号库、影评社区、TOP250 需要长期内容运营与账号体系，与本地优先定位冲突。
- **不要做「另一个 Stash」**：全量刮削、NFO、文件重命名是另一个产品形态，且与在线浏览的心智不同。
- **不要做「另一个 Whisparr」**：种子 / Usenet 索引器涉及下载生态与合规风险，不做。
- **做「多源浏览器 + 本地记忆层」**：源只负责提供内容，拾光负责统一入口、状态、记忆、播放与降级。
- **把多源变成优势而不是负担**：同片归并、选源播放、失败换源，这是单站产品做不到的。

## 4. 分领域深度对比

### 4.1 源聚合：优势在「统一」，缺口在「归并」

拾光把 13 个源做成同一套浏览与播放语义，这是单站产品做不到的。但聚合只做到「放在一起」，没有做到「合在一起」：

- 跨源搜索按源分组，同一部片会出现多次；
- 同一部片在不同源的清晰度、可用性、加载速度不同，用户没有工具判断；
- 播放失败时只能手动回列表换源。

**JavDB / MetaTube / JavSP 的共同做法是先用番号收敛内容，再做展示。** 拾光已有标题解析与艺人匹配能力，补一层「同片键」即可，不必做完整的剧集归一化（该项已明确放弃）。

### 4.2 发现：拾光的节奏更强，深度更弱

- **强**：跨源总榜（最新 / 热榜 / 今天新增）、更新日历、搜索即时命中、结果按源筛选——这些是「每天回来看看」的入口。
- **弱**：进入详情后没有下一步。Stash 的人物页、片商页、标签页会把「一部片」变成「一串片」；JavDB 的相关推荐承担同样作用。
- **建议**：先做零请求版本——用本地快照 + 离线艺人库求交，避免为了「相关」再给站点加请求。

### 4.3 元数据与人物：离线艺人库是护城河

拾光的 `Resources/Catalog/catalog.sqlite` 随 App 离线可查，人物档案还能跨源聚合。这一点比多数在线站更稳：

- 站点失联时，人物资料仍可看；
- 关注人物后可以跨源找新作；
- 不依赖账号与云端。

缺口是「元数据的二次利用」：有了女优 / 片商 / 标签，却没有把它们变成推荐与筛选的入口。MetaTube 的「元数据 → 演员页 → 更多作品」正是这条链路。

### 4.4 观看状态：进度有了，记忆没有

| 层次 | 拾光 | 竞品 |
| --- | --- | --- |
| 看到哪 | 播放进度 + 续看 | 一致 |
| 想看什么 | 稍后看 + 片单 | 一致 |
| 看过之后 | 无 | Stash 评分、JavDB 评分 / 影评、社区脚本评分短评 |
| 精彩在哪 | 无 | Stash 片段标记 |

评分与短评不需要社区，本地 0–5 星 + 一句话即可；片段标记对长片与合集尤其有用。两者都只写本地，和现有「手动标记已看」同一层。

### 4.5 播放：桌面播放器是明显优势

内置查看器支持字幕、音轨、HDR、缓存、悬停预览，且能下载单部视频进图库。JavDB 是网页播放，Stash 是浏览器播放，社区脚本靠改站点播放器——拾光在这一层领先。

缺口在「队列」：下载是单任务串行（`savingItemID`），批量保存时体验会退化。Whisparr 的队列、重试、失败原因值得照搬。

### 4.6 自动化：从「能看到」到「不用找」

Whisparr 的核心不是播放，而是「你订阅，它盯梢」。拾光已经有日历、新内容红点、关注人物新作角标，但缺少一个把它们汇总的入口：

- 「本周关注更新」一屏简报；
- 一键把简报加入稍后看；
- 可选桌面通知。

这不需要账号，也不需要下载，纯本地即可完成，是性价比最高的追更补强。

### 4.7 多端：macOS 单端是现实约束

JavDB、Stash、MetaTube、Whisparr 都有 Web 或多端。拾光短期不应自建云，但可以复用照片主线的「局域网只读 Web 画廊」思路：

- 只读、局域网、带访问口令；
- 只暴露稍后看、片单、关注更新；
- 播放仍在 Mac 上解码，或按 Range 代理。

这比做手机 App 成本低，也更符合本地优先定位。

### 4.8 风险与边界

| 风险 | 现状 | 建议 |
| --- | --- | --- |
| 源改版 / 失联 | 有快照与健康度，但解析失败会静默变空 | 适配器回归自检 + 空列表告警 |
| 第三方内容合规 | 只做索引与播放，不托管内容 | 保持「不托管、不分发、不内置账号」 |
| 下载到本地 | 单部下载进个人图库 | 保持个人使用边界，不做批量分发 |
| 恶意跳转 / 假播放地址 | 解析后直接播放 | 增加播放域名白名单与重定向校验 |
| 隐私 | 状态全本地 | 观看记录不上传；MCP / Web 能力需显式授权 |

## 6. 建议路线

### Phase 1 ·「一个库」

同片键 + 归并展示 + 选源播放 + 详情页相关轨道 + 适配器自检。

完成标志：跨源搜索不再出现同一部片的多张重复卡；详情页能连续浏览三部以上；源解析失败能在构建期发现。

### Phase 2 ·「记得住」

本地评分 / 短评、片段标记、智能片单 2.0、内容屏蔽。

完成标志：用户能按「我打过高分」「有标记」回看；智能片单能按女优 / 片商 / 标签自动更新。

### Phase 3 ·「走出去」

下载队列、追更简报、局域网只读播放、MCP Server / Shortcuts（智能助手侧的 9 个网络资源工具已完成）。

完成标志：不打开源也能知道这周更新了什么；手机上能看稍后看；外部 Agent 能调用搜索与播放入口。

## 8. 结论

拾光网络资源模块已经跨过「能接源、能播」的阶段，下一阶段的主题不是「再接几个站」，而是：

> **把多个源合成一个库，把一次浏览变成一串浏览，把看过变成记得住。**

三件事按顺序做：

1. 跨源同片归并 + 选源播放；
2. 详情页相关轨道；
3. 下载队列与适配器自检（一个补批量体验，一个保长期可用）。

评分、短评、片段标记与追更简报放在其后；Web 多端与 MCP 属于第三阶段，等前两层稳定后再做。
